# Architecture

Seer Classic is a TypeScript and React browser game, released as a browser package for Windows and macOS: the game's files with a small Node.js server that serves them to the player's own browser. Game content is plain JSON under `data/`. Pure rule libraries sit on top of it: the battle engine (`battle/core`), its AI policies (`battle/ai`) and the raising rules (`raising/core`). The application in `src/` is a controller kernel with feature modules, rendered with React. The rules themselves are in [battle/RULES.md](battle/RULES.md) and [raising/SPEC.md](raising/SPEC.md); the rules for changing code are in [AGENTS.md](AGENTS.md). This document describes the code as it is; [architecture-v2](design/notes/architecture-v2.md) is the wave-2 target.

## Principles

1. **Data is plain text.** Species, skills, natures, types, conditions, items, encounters and remake policies are JSON files under `data/`. Rule numbers that are not data are named constants (AGENTS.md rule 3).
2. **The battle engine is a pure, deterministic library.** Its input is two sides, a seed and actions; its output is a list of events. It has no UI, clock, I/O or global randomness, so the same seed and actions replay the same battle.
3. **Presentation is a thin client.** Screens render a snapshot and dispatch actions; they do not compute rules. Rule mirrors still left in components are debt that wave 2 moves into the snapshot.
4. **Skill effects are declarative ops**, with a named `script` escape hatch for unique effects.
5. **Headless first.** Every rule can be exercised from Node without a browser.

## Layers

Imports point down only (AGENTS.md rule 1):

```
src/app          the shell: App, navigation, panels, audio settings, the preview fixture
     ↓
src/kernel       the controller: createGame, dispatch, snapshot, saves
     ↓
src/features/*   battle, raising, collection, items, engravings, challenges, world
     ↓
src/domain       pure content and rules that several features use
     ↓
src/shared       view types, labels, display helpers; src/shared/ui is the UI kit
     ↓
battle/ai
     ↓
battle/core   raising/core
     ↓
data/
```

The gate suite `tools/verification/architecture.mjs` checks every relative import under `src/`, `battle/` and `raising/` (full rules: architecture-v2 §4):

- `battle/core` imports only itself, `raising/core/stats.ts` and `data/`; `battle/ai` only itself, `battle/core` and `data/`; `raising/core` only itself,
  `battle/core/src/rng.ts` and `data/`.
- Features use the kernel only through `contract.ts` (UI-facing), `api.ts` and `acquire.ts`, and feature UI only through `contract.ts`. Another feature is reached through its `index.ts` (headless) or `ui.ts` (screens, for UI code), along `FEATURE_DEPS`: `battle`, `raising`, `items` → `engravings`; `challenges` → `battle`; `world` → `battle`, `challenges`.
- The kernel never imports feature UI or `shared/ui`. Files stay at or under 400 lines, and lines at or under 160 characters.

`architecture-baseline.json` lists the existing offenders and may only shrink: remove fixed entries (`--write-baseline`), never add one. It lists no import violations since wave 2; the remaining entries are oversized files.

The engine never imports an AI policy: `createGameContext` (`src/kernel/context.ts`) injects `battle/ai`'s `AI_POLICY` into every game battle, and the kernel is the only part of `src/` that imports `battle/ai`.

## Data flow

1. **Catalog load.** `loadCatalog()` in `src/domain/catalog/catalog.ts` assembles the catalog from the per-file data (`data/monsters/`, the `skills`, `natures`, `types`, `conditions` and `items` tables, every encounter in `data/bosses/` and `data/trainers/`); `loadCatalogNode()` (`tools/catalog.mjs`) does the same in plain Node for scripts, generators and suites, and the `catalog-loaders` gate checks that both give the same catalog. Other `data/` files are imported by the module that owns them.
2. **The game.** The app opens the save library (`openSaveLibrary` in `src/kernel/save-library.ts`) on the browser's save slots; tests and tools call `createGame(catalog, save?)` (`src/kernel/game.ts`), a game kept in memory. Both build the read-only `GameContext` once with `createGameContext` (`context.ts`: the enriched catalog, the engine data set, the dex, the acquisition routes and families, and lookup indexes), open a save, and get from `runGame` (`controller.ts`) a `GameController`: `snapshot()`, `subscribe()`, `dispatch(action)`, `engravingOptions(uid)`, `exportSave()`, `importSave()` and `reset()`. Its methods are unbound closures, so they are safe to pass directly (`useGame` passes `store.subscribe` unbound).
3. **Dispatch.** Each feature registers a `Feature` (`kernel/api.ts`): its action handlers, the action types allowed while a battle is unresolved, and its slice builder. `kernel/features.ts` lists them, and `contract.ts` composes `GameAction` and `GameSnapshot` from the features' action unions and slice types. `dispatch.ts` routes each action to the one feature that registered it (an unknown or doubly registered type is an error), and accepts only the in-battle actions while a battle is unresolved. It returns a `DispatchResult`: `{ ok: true, notice?, created? }`, where `created` is what the handler reported creating (a bred monster's `uid`, a fusion bead's `itemId`), or `{ ok: false, notice }` when the handler threw. The controller then applies the live save rules (collection credit and shop listings), queues the save write in a microtask and notifies subscribers.
4. **Snapshot.** `snapshot.ts` merges the registered features' slices into one view of everything the UI shows (two features building the same field is an error). `reuseUnchanged` (`structural-sharing.ts`) keeps every unchanged slice and row identical to the previous snapshot's, and the snapshot object itself when nothing changed: `engravingOptions`, the one controller read beside the snapshot, changes only with the monsters and engravingStock slices. So that a dispatch stays within its budget with 200 monsters, the monster rows (`features/raising/view.ts`) are memoised per row and rebuilt only when their record or save fields change; the quests and the fusion and breeding recipes are kept while a key of the save fields they read is unchanged; and the campaign stages build their catalogue parts once per game. A field built as the same object as last time, such as a memo's kept rows, keeps its shared value without being compared again (`fieldSharing`), so rows a memo once rebuilt equal are not compared on every later dispatch.
5. **Screens.** Screens subscribe with `useGame(c, select)` (`src/shared/ui/use-game.ts`) and re-render only when their selection changes identity.

`startSession` (`features/battle/battle-session.ts`) opens every battle. Challenges start their encounters through it (`features/challenges/battle-starts.ts`: Bosses and trainers, Brave Tower floors, campaign stages, facilities) and the world its map contacts (`features/world/training.ts`), each with the `SessionHooks` (`kernel/api.ts`) that settle the challenge: the facilities' missing attempt and clear records, the tower's floor rewards and climb, and campaign progress. `setupBattle` (`battle-setup.ts`) creates each battle through `ctx.createBattle` with the game's script registry ([SCRIPTS.md](battle/core/SCRIPTS.md#game-registries)). `playTurn` submits the player's action and calls `resolveTurn()`, in which the engine asks the policy for each automatic side. A battle left before its first turn, from its loading screen, is dropped by `abandonSession` (the `abandonBattle` action): no result, no settlement, and its attempt taken back. When the battle ends, `settlement.ts` writes HP, PP, experience, captures and rewards back to the save and runs the session's hooks; only then do the events become the battle log and presentation frames, so an error in presenting a turn is reported and cannot drop its settlement.

The battle screen plays each move's original skill effect from its SWF with Ruffle (`@ruffle-rs/ruffle`, self-hosted under `ruffle/` by the `ruffleFiles` plugin in `vite.config.ts`): one host SWF for the page (`skill-effect-host.swf`, `skill-effect-host.ts`), started behind the first battle's loading screen, moved into each battle screen's arena layer and parked between battles, placed at the acting creature as the original client did (`skill-effect-placement.ts`), drawn over both creatures and under the numbers and HUD. `battle-skill-effects.ts` is the loading boundary: `prepareSkillEffects` runs behind each loading screen, `createSkillEffectStage` belongs to the battle screen, and `getSkillEffectTiming` feeds the presentation timing; `skill-effect-session.ts` holds their rules (which screen holds the host, when it is replaced, how an effect is timed), and `data/original-fight-timing.json` the species the original timed by its label table ([skill-effects-ruffle-2026-10-22](design/notes/skill-effects-ruffle-2026-10-22.md), [skill-effects-seamless-2026-10-22](design/notes/skill-effects-seamless-2026-10-22.md)).

## Battle engine

- **Structure.** `engine/battle.ts` is the `Battle` class (state and public API); its methods delegate to the rule modules beside it (`turn`, `move`, `damage`, `effects`, `conditions`, `rules`, …). Automatic sides are decided by the injected `BattlePolicy` (`{ chooseAction, chooseReplacement }`).
- **Rules and numbers.** Turn order, damage, statuses, capture and Boss rules follow [battle/RULES.md](battle/RULES.md). Battle numbers are named in `battle/core/src/constants.ts`, and damage comes from the one engine pipeline (AGENTS.md rule 2); the AI's estimate is its read-only probe (RULES.md section 5.1).
- **Data shapes.** `battle/core/src/types.ts` is the source of truth for species, skills, natures, type data, items, conditions, encounters, battle input and actions, and encounter `variants` carry their `label`. Events are in `events.ts`: `BattleEvent` is a union discriminated by `type`, one member per event the engine emits.
- **Ids and text.** Species ids are the original 精灵 numbers and skill ids the original skill ids; encounters, items, conditions and natures use lowercase slugs (`boss_rei`). Display text is `{ zh, en? }`. Stat keys are `hp atk def spa spd spe`; `acc` and `eva` exist only as battle stages.
- **Types.** The chart is asymmetric: always read `chart[attacker][defender]`. Dual types are stored as arrays, and composite skill types map to their base types.
- **Effects.** Skill effects are ordered ops `{ op, chance?, when?, ... }`, applied after damage unless the op says otherwise. `target` is `self` or `foe`, and `when` takes conditions such as `foe_status`, `self_hp_below_pct`, `first_turn`, `foe_type` or `acted_first`. A `script` op `{ id, params }` names an implementation in `battle/core/src/scripts/`, where `seer_eff_<n>` is original effect template `<n>`. The declarative skill ops:

  | Op | Effect |
  | --- | --- |
  | `stat_stage`, `clear_stages`, `swap_stages`, `copy_stages` | change, clear (`up`, `down`, `all`), swap or copy stat stages |
  | `status`, `cure_status` | inflict a status (a list picks one at random; `level` for 衰弱), or remove it |
  | `add_condition`, `remove_condition` | add a timed condition from `conditions.json` (`turns`, `charges`), or remove it |
  | `heal`, `recoil` | restore HP by `pct_max_hp`, `pct_damage_dealt` or `amount`; the user takes recoil damage |
  | `restore_pp`, `pp_drain` | restore the target's PP; drain the foe's PP |
  | `fixed_damage`, `pct_damage`, `ohko`, `multi_hit` | fixed, percentage and one-hit-KO damage; `min`..`max` hits |
  | `power_if`, `priority_if` | conditional power or priority |
  | `damage_if` | conditional damage multiplier (先出手/后出手 ×2) |
  | `force_switch`, `protect` | force the foe out; block this turn's attacks |

  Boss phases also use `transform`, `set_skills`, `set_ai`, `revive`, `say`, `swap_types`, `counter_skill`, `ohko_below_pct` and `always_crit_below_pct`. The `OPS` table in `engine/effects.ts` is every op the effect interpreter runs (skill effects after the attack, Boss phases, hooks and items); `MODIFIER_OPS` beside it names the five attack modifiers (`multi_hit`, `power_if`, `damage_if`, `priority_if`, `crit_if`), which modify the attack instead of running after it and are applied in `damage.ts` (`damage_if` in `calcAttack`) and `move.ts`.
- **Conditions.** Timed modifiers are hooks on fixed engine extension points (`turn_end`, `modify_damage_taken`, `on_hit`, …). Statuses are conditions with `kind: "status"`, so there is one mechanism.
- **Encounters.** An encounter has a `team`, `rules`, `win`/`lose` objectives, `phases` and an `ai` spec; side kinds are `player`, `wild`, `boss` and `trainer`.
- **Determinism.** One seeded `sfc32` RNG per battle, consumed in a fixed order. The search planner simulates on clones and draws from the live RNG only once, when its chosen strategy is mixed.
- **Turn preparation.** `battle.prepare(side)` decides for an automatic side when its turn opens, exactly as `resolveTurn` would, and stores the decision as its pending action (RULES.md section 11). The battle feature schedules it in an idle slot (`GameDependencies.idle`; by default `shared/idle.ts`: `requestIdleCallback`, or in WebKit a timer set in the next animation frame) after a battle starts and after each turn, and it runs only while that turn still waits. The battle screen's player (`battle-player.ts`) holds those slots from a command until the turn's last frame is on screen, so the preparation runs during the closing frame instead of the playback's first frames and is ready before the commands unlock. The gate `battle-prepare-replay` checks that prepared and unprepared turns replay identically, in the engine and through a controller whose idle tasks run at once, late or never; `battle-ai-latency` checks the search decision budget, and `battle-turn-latency` that a prepared move gives its snapshot within 50 ms.

### AI policies

`battle/ai/src/ai.ts` dispatches on the `ai` spec (`sequence`, `weighted`, `random`, `script` or `smart`).

| Side | Policy |
| --- | --- |
| Wild | `random` among usable moves, unless the encounter sets an `ai` spec. |
| Boss | `smart` is the 裸伤 policy (`legacy-ai.ts`: a knockout first, else the strongest expected-damage attack with a seeded 20% chance of a status move that changes something; [boss-ai-raw-damage-2026-10-21](design/notes/boss-ai-raw-damage-2026-10-21.md)), plus each encounter's authored sequence, weights, phases and scripts ([boss-ai-isolation-v56](design/notes/boss-ai-isolation-v56.md)). |
| Trainer | `smart` is the search planner (`search-ai.ts`, `search/`): it runs the real engine on isolated copies of the battle, models the player only from what has been observed, and plays a mixed-strategy equilibrium ([trainer-search-ai-v58](design/notes/trainer-search-ai-v58.md)). With `allow_switch` it also picks faint replacements. |

## Remake decisions

These are remake decisions, not original rules; do not describe them as original. Later product decisions are in `design/approved-plan.json` and the design notes.

- **No real-time clock.** Hourly windows, weekday-only fights and daily attempt limits are dropped. Weekday objectives and time-window fields become encounter `variants`, which the player picks before the start in the Boss dialogue or the challenge archive (`domain/challenges/encounter-variants.ts`; settled by `features/challenges/boss-variants.ts`, recorded in `game.bossVariants`). 盖亚 pays its essence only when the chosen objective is met, and its fight without one is a practice fight with no record; 厄尔塞拉 and 劳克蒙德 are always fought with one; honours for every variant (七色光羽, 完胜盖亚) come from the cleared variants. Every encounter is open at any time; party and level rules, the attempt-based Boss level rule and campaign and tower order still apply.
- **Open Bosses.** Every Boss is open from the start (user decision, 2026-10-19). The source unlock chains between encounters (the dark-arena doors in order, the second 克莱芬 and 克拉尼特 fights, the Mystery Realm 谱尼 after Tower floor 60) are not enforced; the records keep `unlock.requires` as source history, read only to place that 谱尼 on the Tower panel. Only the stage order inside a campaign and the Brave Tower's floor order gate a fight.
- **New journey.** Three gift starters at Lv 5 and 1000 coins. Ordinary raising, battle and capsule items cost no stock, healing is free, and victories pay coins and pooled experience. A capture is a victory: it counts as a won battle and pays the wild victory's coins and pooled experience; the caught monster, not knocked out, yields no EXP or 学习力.
- **Acquisition.** Wild species are captured with capsules; defeating one does not recruit it. A world-map contact (`startTraining`) is a targeted search: the species' regular Boss encounter (an SPT first), else a capturable wild monster, else a recruit-only challenge that rewards its essence; species listed for recruitment come from SPT recruitment quests. Three journey quests grant one species each. Every capture, essence claim, shop replenishment, fusion or breeding result and evolution respects a six-copy allowance per species, counting unhatched essences.
- **Recruitment.** Initial forms with no habitat, starter, journey, Boss-essence, fusion or breeding route, and paid, VIP or lottery forms, get a collection recruitment (`domain/acquisition/recruitment.ts`; the divine beast, Puni and NPC-partner families are excluded): collect at most six named prerequisites (earlier forms and SPT victories), then claim the essence. The top Brave Tower floor's essence does not count as a route, so 呆呆蛹 has a recruitment as well. A species is repeatable (repeat claims, repeat Boss essences and shop restocks, all within the six-copy allowance) unless `data/acquisition-policy.json` marks it `once`; `unknown` historical repeatability counts as repeatable, the v32 remake choice in `design/notes/acquisition-policy-v32.md`.
- **Bosses are never captured.** A victory that meets the objectives grants the Boss's 精元 essence with its item rewards, and a repeat clear only for a repeatable species. Other Bosses without an original essence or skill reward, except tower floors and intermediate campaign stages, get a remake essence (`domain/catalog/enrichment.ts`) that hatches the initial form of the defeated final form's line (`domain/acquisition/native-acquisition.ts`). Using an essence from the bag hatches it at once into a Lv 1 monster.
- **Traits and engravings.** Every new monster draws one implemented zero-star classic trait (effect 503 is never drawn). Each monster has an ability and a skill slot for the 2013 engravings ([engravings-2013](design/notes/engravings-2013.md)); generic ability engravings are bought one copy at a time, capped at 1 to 6 copies by stat gain, and the others are unlimited (`domain/engravings/engraving-access.ts`, applied when buying, equipping and moving engravings).
- **The editor** (the modifier in settings) changes the same save through the `cheat*` actions.

The game extends the engine when it sets up a battle (`features/battle/battle-setup.ts`): the trait, campaign and NPC-training script registries ([SCRIPTS.md](battle/core/SCRIPTS.md#game-registries)), the attempt-based Boss level rule (`bossEncounterForAttempt` in `domain/challenges/boss-encounter.ts`, from the save's attempts and wins of the encounter), the NPC training profiles (`normalizeNpcTrainingEncounter` in `domain/challenges/npc-training.ts`), and the engravings' stat bonuses and engraved skills (`domain/engravings/engravings.ts`).

## Raising and saves

`raising/core` holds the pure rules of [raising/SPEC.md](raising/SPEC.md); stats come from `raising/core/stats.ts` and are always derived, never stored. A save is the core's `Save` (`raising/core/types.ts`: party, storage, items, pooled experience, progress (the clears, attempts and wins per encounter), the dex and the RNG state) plus the game's `GameExtras` (`src/kernel/save.ts`: coins, traits, quests, engravings, campaign and tower progress, shop listings, recruitment claims). `save.ts` validates saves and upgrades old ones through `MIGRATIONS`, one step per `SAVE_VERSION`; `save-state.ts` starts and opens the journey, and its writer keeps the game's save slot current: at once when a journey is opened, imported or started, and after actions in a microtask (`queueMicrotask`), which runs before control returns to the event loop, so the actions dispatched in one synchronous run (such as one event handler) share one write, and the queued write holds only the save, not the controller; a text equal to the last one written is not written again. An export writes a pending change at once. Every action is therefore handed to the store before the page can paint, run another task (such as the turn preparation) or close. The store keeps any number of save slots in the browser's IndexedDB (`save-slots.ts` over the backends of `slot-backends.ts`; [design note](design/notes/save-slots-2026-10-24.md)): a record and the save's text per slot, and the active slot's id. The save library (`save-library.ts`) plays the active slot; a new save, a load of another slot or an import builds a new controller from that slot's save on the same context, and the app remounts the game under a new key, so nothing of the previous slot carries over. The save of the versions before slots, in `localStorage`, is adopted unchanged as the first slot. A refused write keeps the game running, is shown until a later write succeeds (`SaveProblem.tsx`, with an export button) and is tried again by the next action. A slot whose save cannot be opened is kept, marked unreadable and never written; settings lists it for export, and a new journey opens in a new slot. A battle in progress is not saved, apart from its item use and attempt count. The settings and item windows export and import saves as JSON; an import opens in a new slot. Change the format only through a migration (AGENTS.md rule 7); `golden-saves` checks that saves of released versions still open.

## Verification

- `npm run typecheck` runs `tsc --noEmit`. `npm test` runs the `node --test` unit tests (`*.test.mjs` under `src/`, `battle/`, `raising/` and `tools/distribution/`).
- `npm run verify` runs `tools/verification/run.mjs`, which runs every suite whose status in `MANIFEST.json` is `gate`. The other statuses say why a suite does not gate: `needs-assets`, `needs-browser`, `release` (the browser package: `payload` on its build and staged payload, run by `npm run package`, and `browser-package` on its ZIP), `known-failure` and `tool`. `--status all` runs every registered suite except `tool` scripts, `--jobs N` limits parallelism, and suites can also be named. Logs and `SUMMARY.json` go to `artifacts/verification/`.
- `.ts` suites load through Vite SSR. Suites marked `shards: N` run on N cores through `parallel-shards.mjs`.
- `needs-browser` suites drive the built game in real browsers through Playwright (`playwright-core`, a dev dependency) and `_browser.mjs`: the app is built with Vite into `artifacts/` and served by request interception from that build and `public/` (or, with `SEER_PACKAGE`, by an unzipped browser package's own `server.mjs`), with no listening port; every page is muted. `browser-regressions.mjs` checks the keyboard, focus and clickability fixes of the 2026-10-18 playtest in the system Google Chrome (`SEER_CHROME` names another executable) and, when it is installed (`npx playwright-core install webkit`), in Playwright WebKit as a stand-in for Safari. Its checks are a list of named entries.
- **Boss evidence is for development only** (user decision, 2026-10-19): no screen shows it, and Boss mechanics are to match the original game. `tools/audit/build_boss_evidence_v56.py` writes the ledger `data/boss-evidence-v56.json` (each field's source status) from `data/bosses/` and the user policies of `data/boss-user-policies-v57.json`, four waived mechanics among them (`--check` checks that the ledger is current). The gate `boss-rules-v56` checks that every Boss rule has an implementation and that `data/boss-rule-support-v56.json` is current, and `boss-evidence-controller-v56` that the ledger matches the encounters and that no view carries evidence. A level the original showed as ?? although within the cap (迪符特) is the encounter member's `level_masked`.
- `_harness.mjs` provides Vite SSR loading, a check-and-report `suite()`, memory storage, an offline `fetch` and file hashing. New suites must be registered in `MANIFEST.json`. A behaviour change updates or deletes the old assertions in the same commit.

## Assets

Runtime assets are in `public/`: portraits, battle animations and their HD atlases, the original skill-effect SWFs (`public/battle-effects/swf/`), maps, interface art and audio, each with a manifest that records its source and hashes.
